# 구현 문제점 정리 (에이전트 수정용)

## 목적
이 문서는 `BlazorApp_arduinoSearch_240824_01` 쪽 구현에서 실제로 수정이 필요한 지점을 우선순위별로 정리한 문서다. 에이전트는 아래 항목을 순서대로 처리하면 된다.

## 전제
- 현재 구현은 기본 기능 동작에는 문제 없지만, 여러 장치/여러 페이지/장치 재연결 상황에서 상태가 꼬이기 쉬운 구조다.
- 수정 후에는 `dotnet test BlazorApp_arduinoSearch_240824_01/BlazorApp_arduinoSearch_240824_01.sln --configuration Release --no-restore` 로 회귀 테스트를 확인해야 한다.

## P0: 즉시 수정 권장

### 1) MQTT 연결 세션이 페이지 간에 섞일 수 있음
- 위치: `BlazorApp_arduinoSearch_240824_01/Services/MqttService.cs`, `Pages/LedControl.razor`, `Pages/SensorChart.razor`, `Pages/DhzChart.razor`
- 문제:
  - `MqttService`가 하나의 연결 상태를 공유하고, 각 페이지가 이벤트를 구독한다.
  - 페이지 전환, 장치 변경, 재연결이 발생하면 이전 페이지의 핸들러가 남아 있거나 새 연결 상태가 기존 구독자에게 전달될 수 있다.
  - 특히 같은 브라우저 세션에서 여러 장치 화면을 열었을 때 메시지 수신이 꼬일 수 있다.
- 수정 방향:
  - `MqttService`를 “연결 세션” 단위로 관리하도록 리팩터링한다.
  - 각 페이지/뷰는 자신만의 연결 식별자와 구독 토큰을 갖도록 만든다.
  - 구독/해제 로직을 명시적으로 관리하고, 페이지 종료 시 이벤트를 해제한다.

### 2) 장치 라우팅이 장치 이름 문자열에 의존함
- 위치: `BlazorApp_arduinoSearch_240824_01/Pages/Devices.razor`
- 문제:
  - `ResolveDeviceRoute()`가 `device.Name.Contains("LED")`, `Contains("DHZ")` 같은 문자열 비교로 분기한다.
  - 장치명이 바뀌거나 새로운 장치 유형이 추가되면 로직이 쉽게 깨진다.
- 수정 방향:
  - `Device` 모델에 `DeviceType` 또는 `Capabilities` 같은 명시적 속성을 추가한다.
  - 라우팅은 이름 문자열이 아니라 타입/기능 기반으로 결정하도록 바꾼다.

### 3) 차트 JS 상태가 페이지 전역으로 공유되어 충돌 가능성이 있음
- 위치: `BlazorApp_arduinoSearch_240824_01/wwwroot/js/sensorChart.js`, `Pages/SensorChart.razor`, `Pages/DhzChart.razor`
- 문제:
  - `chartSets`가 JS 모듈 전역 상태로 관리되어, 페이지 이동/다중 인스턴스 상황에서 차트가 이전 인스턴스와 섞일 수 있다.
  - 한 화면에서 차트가 초기화되지 않은 상태로 재렌더링되면 업데이트가 누락되거나 이전 차트가 남을 수 있다.
- 수정 방향:
  - 차트 인스턴스를 페이지/컴포넌트별로 분리한다.
  - `initialize`/`update`/`dispose`가 특정 DOM 요소와 인스턴스에 대한 식별자를 기준으로 동작하도록 변경한다.

## P1: 구조 개선과 안정성 보강

### 4) 장치 검색 로직이 네트워크 조건에 매우 취약함
- 위치: `BlazorApp_arduinoSearch_240824_01/DeviceDiscoveryService.cs`
- 문제:
  - 현재는 Ping 성공 후 HTTP 요청으로 장치를 판별한다.
  - 네트워크 환경에 따라 Ping이 실패해도 실제 장치가 존재할 수 있고, 반대로 Ping은 통과했지만 HTTP 응답이 불안정할 수 있다.
  - 검색이 느리고, 실패/성공을 구분하기 어려워 UI와 로깅 품질이 떨어진다.
- 수정 방향:
  - 장치 검색 전략을 `Ping + HTTP` 조합에서, 설정 가능한 `ProbeStrategy` 형태로 분리한다.
  - `unreachable`, `http_error`, `invalid_payload`처럼 상태를 구분해 UI에 표시한다.
  - 검색 대상 목록과 제외 IP 정책을 더 명시적으로 관리한다.

### 5) 장치 설정 모델이 문자열 기반이라 타입 안정성이 낮음
- 위치: `BlazorApp_arduinoSearch_240824_01/Models/Device.cs`, `Pages/Devices.razor`
- 문제:
  - MQTT 포트가 문자열로 저장되므로 파싱 오류와 검증 누락이 발생하기 쉽다.
  - 사용자가 입력한 값이 UI에서만 검증되고, 서버 측 검증이 분산되어 있다.
- 수정 방향:
  - `Device` 모델의 `MqttPort`를 `int` 또는 `int?`로 바꾸고, `MqttServer`, `MqttTopic`에 대한 서버 측 검증을 추가한다.
  - `Devices.razor`는 값 검증만 담당하고, 실제 저장/전송은 모델 객체를 기준으로 처리하도록 정리한다.

### 6) 센서 메시지 파싱/차트 업데이트의 예외 처리와 데이터 정책이 충분하지 않음
- 위치: `BlazorApp_arduinoSearch_240824_01/Services/SensorPayloadParser.cs`, `Pages/SensorChart.razor`, `Pages/DhzChart.razor`
- 문제:
  - 현재는 JSON 오브젝트가 아니면 실패하고, 잘못된 필드값은 단순히 UI에 에러만 표시한다.
  - 잘못된 메시지나 비정상 토픽이 계속 들어오면 차트가 오염되거나 상태가 엉킬 수 있다.
- 수정 방향:
  - 파싱 실패 메시지를 `drop`, `retry`, `invalid` 같은 상태로 구분한다.
  - 차트에 들어가는 데이터의 최대 길이/압축 정책을 명확히 정한다.
  - 파싱 실패 시 차트 갱신을 중단하고, 상태 메시지를 더 명확하게 보여준다.

## P2: 회귀 방지용 테스트 보강

### 7) MQTT/라우팅/다중 페이지 시나리오 테스트가 부족함
- 위치: `tests/BlazorApp_arduinoSearch_240824_01.Tests`
- 문제:
  - 현재 테스트는 장치 검색 후보 IP 생성, MQTT 쿼리 파싱, 센서 페이로드 파싱에만 초점이 맞춰져 있다.
  - `MqttService`의 재연결/구독 해제, 라우팅 분기, 다중 페이지 차트 초기화는 검증되지 않는다.
- 수정 방향:
  - `MqttService`에 대한 연결/재연결/구독 해제 테스트를 추가한다.
  - `Device` 타입 기반 라우팅 로직에 대한 테스트를 추가한다.
  - 차트 초기화/파괴 로직의 JS 모듈 테스트(또는 최소한의 컴포넌트 테스트) 범위를 확장한다.

## 권장 작업 순서
1. MQTT 연결 세션 분리
2. 장치 타입/기능 기반 라우팅 도입
3. 차트 JS 인스턴스 격리
4. 장치 검색 전략 보강
5. 모델/검증 구조 정리
6. 테스트 추가

## 완료 기준
- 각 항목별 수정 후 빌드와 테스트가 통과한다.
- 페이지 전환/장치 변경/재연결 상황에서 메시지 오염이 발생하지 않는다.
- 장치 유형이 바뀌어도 라우팅 로직이 깨지지 않는다.
